二、006-R1-A：修正出生时点与路程裁短
2.1 “提交时不推进”已经成立，“出生当步不推进”还没有成立

当前管理器会在 _physics_process() 中把所有 pending 炮弹改成 flying，随后立即调用 advance_projectile()，没有比较 born_physics_tick。

这会造成两种不同结果：

正常车辆在管理器之前发射：
本 tick 接收 → 本 tick 管理器立即推进。

演示在管理器之后发射：
本 tick 接收 → 下一 tick 才轮到管理器。

你现在的演示恰好设置为优先级 200，在管理器 100 之后直接调用 Gunner.try_fire()，因此没有覆盖正常车辆在管理器之前发射的情况。Godot 的物理回调优先级确实会影响执行先后。 
Godot Engine documentation

现有“出生当步不推进”测试只在 try_spawn() 返回后同步检查 status=pending，随后等待物理帧；它证明接收函数没有立即推进，不足以证明该物理 tick 的后半段也不会推进。

最小修法

删除“无条件批量晋升 pending”的逻辑，在唯一推进循环里明确检查：

gdscript
var now_tick := Engine.get_physics_frames()

for pid in _active.keys():
	var st: ProjectileState = _active.get(pid)
	if st == null or st.is_terminal():
		continue

	# 出生 tick 无论在管理器之前还是之后提交，都不能推进。
	if now_tick <= st.born_physics_tick:
		continue

	if st.status == "pending":
		st.status = "flying"
		_pending.erase(pid)

	advance_projectile(st, delta, snapshots, space)

这是接入片段，保留现有每步一次快照采集，不再建立第二个推进器。

验收增加两个提交时机：管理器之前、管理器之后。两者都必须在出生 tick 保持位置、年龄、路程不变，下一 tick 才推进。不要通过调整演示优先级绕开检查。

同批修正 active_states()：当前先遍历 _active，又把 _pending 中的对象追加一次，但 pending 已经在 _active 内，导致出生阶段同一发被返回两次。只从 _active 枚举一次即可。

2.2 查询裁短了，但炮弹仍被提交到完整终点

当前代码正确计算了：

query_len = min(剩余路程, 本子段长度)

但在没有碰撞时，仍执行：

gdscript
st.position_world = cand_p
st.velocity_world = cand_v
st.age_s += h
st.travelled_m += seg_len

这里使用的全部是未裁短的子段。碰撞分支也仍然计算 contact_time = h * t_frac，没有考虑查询线段已经被缩短。

一个不涉及引擎误差的反例：

关闭重力，速度 300 m/s，子步 1/60 s。
完整子段长 5 m，但只剩 2 m 射程。

当前：查询 0～2 m，没有碰撞，却提交位置 5 m。
应当：停在 2 m，终止为 expired_distance。

若这段查询在前方 1 米处碰墙：

1 m 是裁短后 2 m 线段的 50%。

当前用时：1/60 × 0.5 = 0.008333 s
正确用时：1/60 × (2/5) × 0.5 = 0.003333 s

这些结果已经由独立 Python 检查复现；它们是当前状态提交规则的数学反例，不是 Godot 实机轨迹。

统一使用同一个裁短比例

在现有分段折线近似下：

gdscript
var alpha := minf(1.0, remaining / seg_len)
var query_end := st.position_world.lerp(cand_p, alpha)
var query_length := seg_len * alpha
var used_h := h * alpha

之后统一处理：

情况	位置、时间和路程
无接触、未裁短	接受完整子段
无接触、已到路程上限	接受 query_end、used_h、query_length，立即到期终止
裁短段内发生接触	接触用时为 used_h × event.t，位置取真实查询接触点
接触恰在允许端点	先处理该接触，否则才判到期

速度也用相同的实际用时更新，不能位置停在 2 米、年龄和速度却跑完 5 米。

这沿用本单已授权的折线近似，不要求实现精确曲线弧长反解。 剩余距离接近零时也不要直接增加完整 h。

新增检查要验证终止记录中的位置、路程、时间，而不只是检查字符串等于 expired_distance。目前路程到期测试主要检查终止原因，正好漏掉了这项越界。

三、006-R1-B：补完整发射身份、暂停入口与终止顺序
3.1 同名新车的第一发会被旧车的编号挡住

当前去重键是：

gdscript
"%s:%d" % [shooter_id, shot_id]

没有生命周期。旧车 Y 发过第 1 发后，同名新车 Y 即使拥有新的 life_id，其第 1 发也会得到 duplicate_launch。当前测试虽然重建了 Y，却没有让新 Y 再次开火，因此没覆盖这个问题。

改为完整发射身份，例如：

gdscript
var launch_key := JSON.stringify([
	int(spec["round_id"]),
	str(spec["shooter_id"]),
	int(spec["shooter_life_id"]),
	int(spec["shot_id"])
])

同一轮次、同一生命周期、同一射击编号重复提交应拒绝；新生命周期的同名车可以正常发射。

同时校验生命期身份有效。训练场当前使用 round_id=0，可以继续明确允许这个训练值，不必为了统一接口伪造任务轮次。

3.2 暂停停止回调，不等于公开发射方法自动拒绝

当前 Gunner.try_fire() 和 ProjectileManager.try_spawn() 都没有显式的树暂停检查。正常输入回调暂停后不会调用它们，但测试脚本或 ALWAYS 节点仍可以直接调用。在弹药充足、冷却和宽限均为零的前提下，目前入口没有依据暂停状态拒绝发射。

在两个公开入口先检查：

节点仍有效且在树中
没有退出／清理
SceneTree 没有暂停
依赖组件有效

暂停拒绝必须发生在扣弹、占用容量和修改发射编号之前。清理期间也暂时拒绝新发射，避免重置回调中又生成一发。

测试应分别验证：

暂停 + 无冷却 + 有弹 → Gunner 拒绝，账本不变。
暂停 + 合法 spec → Manager 拒绝，活动数量不变。
恢复 → 新的合法请求能够发射。

不能用冷却或无弹导致的拒绝，替代暂停条件的验证。

3.3 世界撞击仍在“终止提交之前”调用外部对象

车辆路径通过 finish_once() 后再分发，这是正确方向。但世界接触分支当前顺序是：

collider.register_hit({})
→ 更新炮弹状态
→ finish_once()

如果世界对象的命中回调触发重置，当前炮弹仍在 _active 中，可能先被取消，然后原来的 impact_world 终止无法再登记。“先终止，再通知”的保证还没有覆盖世界接触。

统一为：

计算最终状态和记录
→ 标记 terminal
→ 从 _active / _pending 移除
→ 再分发车辆或世界反馈

不要求新事件框架。可以调整现有 finish_once() 与分发入口，但世界对象引用只供当次立即使用，不能放进长期保存的记录。

新增一个小型世界目标：它在 register_hit() 中调用场景重置。验证该发只产生一次正确终止，其他在飞弹被正常取消，不重复计分，也不访问已释放对象。

另外，Main._on_projectile_finished() 当前在调用目标 register_hit() 前没有检查记录轮次。轮次检查应放在目标反馈之前，不能只让任务 gate 拒绝计分，而目标的 hits_taken 已经增加。
