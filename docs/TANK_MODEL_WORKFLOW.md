# 约 1000 三角面坦克模型：可复用制作与移植流程

版本：1.0 · 2026-09-09 · 适用于 MCTHUNDER 当前四款正式车型。

本流程的目标是：用约 1000 个三角面保留坦克的车型轮廓和机械结构，用固定贴图表现轮辐、螺栓、焊缝、舱盖、格栅和履带链节，交付可编辑 Blender 源文件、可导入的 GLB，以及能够验证复刻结果的参数、脚本和记录。

**复刻现有模型，以保存的贴图、种子数据、脚本和工具版本为准。** 概念图和提示词负责表达方向，不能替代这些源文件。重新调用图像生成服务会得到新的纹理；使用包内固定 PNG 才能复刻本次纹理。相同模型数据不等于所有机器上截图逐像素相同，灯光、渲染器、曝光、抗锯齿和显卡也会影响画面。

## 1. 已交付模型与计数口径

| 车型 | 稳定 ID | 完整模型三角面 |
|---|---|---:|
| M4A3(75)W / 1944 / VVSS | `us_m4a3_75w_vvss_1944` | 1016 |
| M24 / M6 / T85E1 / 1951 | `us_m24_m6_t85e1_1951` | 908 |
| M26(T26E3) / M3 / 1945 | `us_m26_m3_1945` | 1018 |
| M36 / M4A1 mount / 1945 | `us_m36_m4a1_1945` | 970 |

计数包括车体装甲、炮塔、炮盾、炮身、两侧履带、轮组、悬挂和外部附件。计数不包括地面、摄影灯、相机、HUD、瞄准标记、炮口火光、爆炸和烟雾。正式模型硬上限为 **1100 三角面**；包含预分配效果的游戏实体另设 3000 三角面上限，二者不能混写。

Blender 的一个四边面导出后通常成为两个三角面，不能用未三角化的“面数”代替导出预算。当前生成器对实际网格应用 Triangulate，再计数；Godot 对实际运行模型再次计数，并与 manifest 中的值相等比较。

`authoring/poly_budget/textured/m4_textured_1000.blend` 是设计预览样件，最终为 1051 三角面。它与正式 M4 的 1016 三角面文件用途不同：预览用于评估表现，正式车使用游戏的装甲种子与运动轴系。移植游戏应选 `authoring/vehicles/` 和 `assets/vehicles/` 中的正式资产。

## 2. 复刻必须保存的文件

推荐在新项目内保留以下相对目录；脚本按自身位置寻找工程根，不依赖启动终端的位置。

```text

├─ MODEL_BASELINE.json               已验证的几何、UV、轴心指纹
├─ authoring/
│  ├─ REBUILD_MODELS.ps1             一键重建与比对入口
│  ├─ vehicles/
│  │  ├─ build_textured_lowpoly.py   当前正式生成器
│  │  ├─ style_metadata.py          材质/元数据辅助
│  │  ├─ repro_report.py            独立复刻检查器
│  │  ├─ export_current.py          导出手工编辑后的源文件
│  │  ├─ seeds/*.json               四车参数及装甲局部顶点/三角形
│  │  └─ *.blend                    四车可编辑源文件
│  └─ poly_budget/
│     ├─ build_preview.py           共用几何构造函数
│     ├─ texture_preview.py         共用 UV 分区函数及预览流程
│     └─ ATLAS_PROMPT.txt            完整图集生成提示词
├─ assets/
│  ├─ art_palette.json
│  └─ vehicles/

```

`build_textured_lowpoly.py` 会导入 `poly_budget` 中的两个模块；移植时不能只复制它一个文件。Blender 源文件和 GLB 内嵌了纹理，游戏的运行时装甲及履带材质还读取独立 PNG，因此 PNG 也必须一起交付。

工具程序不装入资产包：Blender、Godot、`.godot/` 缓存、临时备份和自动生成的导入缓存均不属于模型源资产。

## 3. 从移植包复刻当前四车

准备 **Blender 5.2.1 LTS 普通版**。本流程仅使用随 Blender 提供的 Python、`bpy`、`mathutils` 和 glTF 导出器，不需要安装第三方 Blender 插件、Python 包或调用外部 API。

解压移植包，在包的根目录运行：

```powershell
& ./authoring/REBUILD_MODELS.ps1 -BlenderPath '你的 Blender 目录/blender.exe' -Verify
```

这个命令会重建四个 `.blend`、GLB 和车型 manifest，然后逐车检查并写出 `MODEL_REPRO_REPORT.json`。应在移植包副本或独立工作目录中运行，因为重建会替换其中的同名模型文件；已有手工编辑先另存版本。

成功时必须看到：

```text
LOWPOLY_MODEL_PASS ...
REPRO_MODEL_PASS ...
REPRO_BASELINE_MATCH_PASS
REBUILD_MODELS_PASS: ...
```

验证器比较：Blender 版本、固定贴图 SHA256、种子 SHA256、模型三角面数，以及对象名称/父子关系/局部变换/顶点/面索引/UV 的规范化指纹。它还独立比较每一片装甲与种子中的顶点和三角形。指纹中的浮点数保留六位小数，适用于以米为单位的本资产。不要用 `.blend` 文件整体哈希判断跨机器重建是否相同：文件容器和保存元数据可能变化。

只生成一款车可以直接调用 Blender：

```powershell
& '你的 Blender 目录/blender.exe' --background --threads 4 --python-exit-code 1 `
  --python ./authoring/vehicles/build_textured_lowpoly.py -- us_m4a3_75w_vvss_1944
```

只打开已有 GLB 看模型不需要重建，也不需要 Blender。需要改形状和 UV 时打开 `.blend`。

## 4. 制作新车型前先填写规格卡

每一款车先单独确定以下信息，不要把不同年份、炮型和悬挂型式拼在一起：

| 项目 | 必填内容 |
|---|---|
| 身份 | 国家、车型、亚型、年份、炮型、悬挂型式、唯一 ID |
| 外形参考 | 正面、侧面、后面、顶面，以及必要的局部结构图 |
| 尺寸 | 车体长、总宽、车体高度、炮塔高度、炮身长度 |
| 机械关系 | 负重轮数量与间距、主动轮位置、诱导轮位置、悬挂连接方式 |
| 动作关系 | 炮塔旋转轴心、炮耳位置、后坐方向、炮口位置 |
| 装甲关系 | 哪些表面参与命中，哪里是开口，哪些只是装饰 |
| 材质风格 | 基础车漆、橡胶、裸钢、帆布、标识与磨损程度 |
| 预算 | 目标约 1000 三角面，上限 1100；纹理尺寸与材质数量 |
| 证据状态 | 已确认尺寸、估算尺寸、概念设计分别标明 |

概念图用于造型和材质方向。尺寸、轮数、车型身份和装甲规则使用经过确认的资料或项目参数。图中标注“2.5K triangles”等文字不代表最终导出统计，本次用户已选择约 1000 三角面。

在当前项目中，新车型配置先通过内容验证，再由 `tests/export_historical_model_seed.gd` 导出种子。独立移植包已经附有四车种子，复刻它们不需要运行整个游戏。

## 5. 把预算花在真正需要的地方

先建决定轮廓的部分，再分配剩余面数。以下是约 1000 三角面车型的参考分配，不是各车必须相同的硬比例：

| 部分 | 参考三角面 | 原则 |
|---|---:|---|
| 车体、炮塔、炮盾装甲 | 170–230 | 保留斜率、转折、开口和查询拓扑 |
| 两侧轮组 | 300–360 | 低边数圆柱，轮面机械细节用图 |
| 两侧履带带体 | 130–170 | 连续轮廓，用贴图表现重复链节 |
| 主炮与炮口 | 70–110 | 保留直径变化、真实开口和必要制退器 |
| 悬挂连接 | 50–90 | 让轮子与支承结构有可见连接 |
| 舱盖、机枪、天线、行李等 | 80–150 | 优先影响轮廓或动作的部分 |

判断一个细节是否建模，用三个问题：

1. 从正常游戏距离看，它会不会改变轮廓或遮挡关系？
2. 它会不会独立运动，或者形成必须看见的开口？
3. 玩家是否需要近距离从侧面看出它的厚度？

答案都是否，优先放进贴图。轮辐凹孔、轮毂螺栓、焊缝、平面标识、散热格栅、舱盖接缝和履带链节适合纹理；炮管、轮胎宽度、连接悬挂、炮塔整体、突出机枪、天线、外置行李适合几何。

不要给每个螺栓建圆柱，也不要为每片履带复制一个立方体。本项目旧实现曾因此达到每车约两万三角面，新正式模型已替换这部分结构。

## 6. 灰模与机械结构

先只看灰模的前、侧、后、顶和斜前视图，检查车体比例、炮塔位置、炮身长度、履带接地轮廓、轮数和轮距。灰模不合格时不要用漂亮贴图掩盖问题。

车体以多层轮廓环连接成斜甲；炮塔用少量分面表达铸造或焊接形体；炮盾与炮塔保持各自的运动关系。平板只在轮廓、装甲分区或贴图区域需要时细分，不要为了显得精细随意加线。

轮子采用低边数圆柱。外侧圆面保留真实面积，轮面图案映射其上；贴着车体、不可见的内侧封口可以省去。轮子不能互相穿插，主动轮、诱导轮和负重轮应能区分。VVSS 必须能看出成对轮组和悬挂连接，扭杆悬挂保留独立摇臂关系。

履带带体沿轮组外围形成闭环。实际导出必须包含两侧，不可只统计镜像前的一半。链节重复由贴图承担，带体分段用于弯曲轮廓及控制纹理拉伸。

主炮至少保留根部、炮身收缩和炮口内壁。不要用一个黑色圆片冒充任何视角都成立的炮口；开口模型需要能够从斜前方看出内壁。当前开口炮塔 M36 不能封上一块顶板。

## 7. 概念图转固定纹理图集

本次采用“概念图作为风格与机械细节参考 → 生成平面图集 → 给低模做 UV”路线。没有把整张透视概念图直接投射到整个坦克上。

当前图集由内置 ImageGen 生成，原始成品是 `vehicle_concept_atlas_v1.png`，实际 **1254×1254**。提示词虽然请求了 2048×2048，交付以工具实际返回的尺寸为准，不把请求参数当成结果。4×4 分区使用归一化 UV，因此不依赖像素边长恰好能被 4 整除。

四列四行的分区从左上开始排列：

| 行 | 第 1 列 | 第 2 列 | 第 3 列 | 第 4 列 |
|---|---|---|---|---|
| 1 | 普通橄榄色车漆 | 深色车漆 | 负重轮正面 | 主动轮正面 |
| 2 | 四段重复履带链节 | 车体正面星标甲板 | 炮塔侧面星标甲板 | 发动机格栅 |
| 3 | 车体侧板 | 圆形舱盖 | 车体后板 | 悬挂机械面 |
| 4 | 橡胶 | 裸钢 | 帆布绑带 | 驾驶员舱盖 |

完整可复用提示词见 `authoring/poly_budget/ATLAS_PROMPT.txt`。重做图集时应明确：平面二维纹理、严格等分区域、区域顺序、正交正面、统一中性光、禁止整车透视图、禁止标签和装饰边框。生成后先逐格查看，再做 UV。

纹理不应带明显环境投影，否则在游戏中会出现与灯光相反的阴影。允许少量绘制的凹槽暗部和边缘磨损，用于表现细节；本次只有基础颜色图，没有额外法线图、粗糙度图或高度图。需要增加这些通道时，必须同步更新材质、导出和验证，不要在文档中把未制作的通道写成已有功能。

## 8. UV 映射操作要点

不要让车体、轮子、履带共用同一套随意展开结果。按机械含义分配区域：

1. 轮面：以实际轮心为中心做平面径向映射，外轮廓与纹理圆对齐；半径不同的轮子分别按自己的半径归一化。
2. 履带：每段外侧面映射重复链节区域；几何分段控制重复密度。内侧、侧壁使用钢材区域，避免侧壁出现横向拉伸的完整履带板。
3. 车体斜甲：同一装甲区域使用一致的平面投影范围，星标跨两个装甲子片时要连续。
4. 炮塔侧面：选择适合的侧片放标识，其他片用普通车漆。不要把越界 UV 全压到图集边缘，这会把边缘磨损拉成整条条纹。
5. 后甲与顶面：后板、散热格栅、圆舱盖、驾驶员舱盖分别使用对应区域。
6. 外部行李和轮胎：分别使用帆布、橡胶区域，避免所有部件都像同一种涂漆金属。

图集函数 `tile_uv()` 在每格内部留约 1.8% 安全边距，减少采样到邻格。低分辨率远景仍应实测 mipmap 串色；如果以后缩小纹理或提高各向异性过滤，需要重新看远景。

Blender UV 使用左下方向约定，当前 Godot 运行时装甲 UV 需要做 `v = 1 - v`。GLB 导出/导入已经处理自己的纹理坐标，不要再额外翻转 GLB 外饰。`VehicleAtlas` 只对 manifest 中保存的 Blender 装甲 UV 翻转一次。

标识不能因为贴满一块面而变得宽扁。预览阶段必须看正侧面：星标、圆舱盖和轮毂圆形应保持合理比例。

## 9. 节点、轴心与动作

正式结构：

```text
hull                       车体；车辆整体运动
├─ Armor_*                 对应装甲种子中的车体片
├─ Cosmetic_*              轮组、悬挂、履带、附件
└─ turret                  相对车体的炮塔水平旋转轴
   ├─ Armor_*              炮塔装甲片
   ├─ Cosmetic_*           舱盖、机枪、天线等
   └─ barrel               炮耳/俯仰轴
      ├─ Armor_*           独立运动的炮盾/转子装甲
      └─ gun_recoil        只承载后坐的炮身外观
         └─ Cosmetic_*     主炮、炮口、必要制退器
```

1 单位为 1 米。游戏侧 +Y 向上、前方 -Z；建模函数将游戏坐标 `(x,y,z)` 转为 Blender `(x,-z,y)`，再通过 glTF Y-up 导出。导出前不随意把层级局部变换烘焙为世界坐标。

炮塔必须围绕正确位置旋转，炮管俯仰必须围绕炮耳，炮身后坐沿炮管轴回退。测试不能只看静止模型：至少检查炮塔左右转动、俯仰极限、后坐，以及游戏炮口标记是否在可见炮口处。

## 10. 保持装甲外观与命中一致

`Armor_*` 与 `Cosmetic_*` 的含义必须一直保持：前者来自实际装甲布局，后者提供外观，不增加有效装甲。运行时将装甲按 hull/turret/barrel 合批，但每个顶点和三角形仍来自同一查询布局。

`seeds/*.json` 保存各片装甲的局部顶点、三角形索引、运动部件和装甲区域。`*.manifest.json` 的 `armor_uv` 为同一批顶点提供纹理坐标。Godot 在原有顶点上附 UV，不另建一个形状近似但位置不同的外壳。

新增装饰不能遮盖错误的装甲轮廓。改装甲外形时同时改参数/布局并重新导出种子；只改 `.blend` 的装甲会被验证器拒绝。厚度、穿甲、模块和伤害数值不由颜色、贴图凹槽或装饰螺栓决定。

炮塔脱离、车辆重置和暂停也要检查。当前游戏的殉爆会移动实际炮塔节点，命中查询跟随同一个节点；不能留下原位置的隐形装甲。这个行为是游戏集成逻辑，不是 GLB 文件自动提供的功能。

## 11. Blender 保存与导出

正式重建使用 `build_textured_lowpoly.py`。它是确定性的建模脚本，不会再次生成纹理。生成前保存手工修改；生成后 `.blend`、GLB、manifest 和独立纹理应一起版本管理。

手工编辑现有源文件后，用保留编辑的导出器：

```powershell
& '你的 Blender 目录/blender.exe' --background `
  ./authoring/vehicles/us_m26_m3_1945.blend --python-exit-code 1 `
  --python ./authoring/vehicles/export_current.py
```

手工导出需要重新生成复刻报告，并在确认修改后更新基线。不要为了让检查变绿直接覆盖基线；先检查模型和差异。UV 接缝应放在装甲片边界，避免同一装甲顶点被赋予无法在当前 manifest 中表示的多个 UV。

建议命名规则：车型 ID 用稳定英文标识；新贴图用 `v2`、`v3` 等版本后缀；对外发布模型保留已验证的源版本。不要用“最终版2最终版”或只靠截图找资产。

## 12. 导入 Godot 及迁移其他工程

在当前完整游戏工程中执行：

```powershell
& ./tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path . --editor --import
& ./tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path . -s res://tests/run_blender_asset_checks.gd
& ./tools/godot/Godot_v4.7.2-stable_win64_console.exe --headless --path . -s res://tests/run_art_checks.gd
```

工具版本为 Godot **4.7.2-stable 普通版**，渲染器 `gl_compatibility`。Blender 不参与游戏启动。移植包不包含完整游戏类和引擎，上述 Godot 检查命令应在完整 MCTHUNDER 工程中运行，不能在仅有模型的包里直接执行。

普通 Godot 项目可先直接实例化 GLB。若要移植当前装甲/动作系统，还需要按目标工程适配 `HistoricalVehicleModel`、`VehicleAtlas`、`HistoricalTrackMotion`、装甲布局、车辆控制和生命周期接口。包内 `integration_reference/` 只提供这些集成参考，不是假称开箱即用的独立游戏插件。

两侧履带使用 `vehicle_tracks.gdshader`，仅滚动图集中的履带区域。相位来源是实际车体位移和转角；左右侧分别计算，因此原地转向时应出现相反的移动方向。重置清零，暂停冻结。动画不得反过来控制车辆位置或改变碰撞。

迁移其他引擎时逐项核对：坐标轴、米制比例、前向、材质颜色空间、UV 原点、法线绕序、双面设置、粗糙度、透明度、层级父子关系、炮塔轴心和炮口。不要靠旋转整个模型“看起来朝前”后就跳过轴心检查。

## 13. 必须通过的验收

| 检查 | 方法 | 合格标准 |
|---|---|---|
| 面数 | Blender 实际三角化 + Godot 实际运行统计 | 完整模型 ≤1100，导出与运行时相等 |
| 结构 | 前/侧/后/顶/斜前视图 | 轮数正确、悬挂相连、无明显相交与悬空 |
| UV | 轮面、星标、舱盖、履带近景 | 无串格、倒置、严重拉伸、重复标识 |
| 法线 | 法线与实际三角形绕序逐片比较 | 不因错误法线出现黑面、消失或不正确受光 |
| 轴心 | 左右转炮、俯仰、后坐 | 运动中心正确，炮口与可见炮口一致 |
| 装甲 | 种子/导出/运行查询几何比较 | 顶点、三角形与部件归属相同 |
| 动画 | 行驶、倒车、原地转向 | 履带方向合理，左右侧独立 |
| 生命周期 | 暂停、恢复、重置、死亡 | 无残留相位跳变、丢材质、旧碰撞 |
| 可移植性 | 新目录中重建并比对基线 | `REPRO_BASELINE_MATCH_PASS` |
| 打包 | 只加载 PCK，断开源工程回退 | GLB、manifest、图集、shader 均可加载 |
| 性能 | 八车实战窗口测量 | 报告真实硬件、帧耗时和绘制量，不以面数代替测量 |

正常玩家视角和模型观察视角都要有截图，二者分别标注。自动通过证明指定检查通过；截图目视和真人审美意见分别记录，不相互代替。

## 14. 常见失败与对应处理

| 表现 | 常见原因 | 处理 |
|---|---|---|
| 轮子像黑色实心饼 | 轮面未映射、边数/大小错误、互相重叠 | 先核对轮心半径与间距，再映射轮面格 |
| 星标变成长条 | 把正方形纹理拉满长侧板 | 改投影范围或选合适侧片，保持比例 |
| 炮塔出现长条磨损纹 | 越界 UV 压在某条纹理边缘 | 无标识片改用普通车漆，不拉伸边缘 |
| 车体突然出现轮子图案 | 图集行列或 V 方向弄反 | 分别检查 Blender UV 与 Godot manifest 翻转 |
| 侧板像纸片 | 重要轮廓厚度被省略 | 为该轮廓保留厚度，平面细节继续用图 |
| 履带面数暴涨 | 每片链节和垫块都用了实体网格 | 换连续带体，使用纹理滚动 |
| 能看到却打不到 | 外观壳与实际装甲使用不同几何 | 统一布局数据，逐片比对 |
| 转炮后模型错位 | 父子层级或局部轴心被烘焙错 | 恢复 hull/turret/barrel/gun_recoil 关系 |
| Blender 好看，游戏很暗 | 曝光、环境光、颜色空间、材质或纹理过滤不同 | 固定两端设置，实机查看；不要只交棚拍图 |
| 换电脑生成不一样 | 工具、脚本、参数或纹理发生变化 | 对照版本和复刻报告，不重新生成随机纹理 |
| 在本机能用，打包缺材质 | 依赖留在私人目录或只有导入缓存 | 纹理、GLB、manifest 与 shader 使用工程相对路径 |
